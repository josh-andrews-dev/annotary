# Releases, the tap and the update notice

A release is a pushed tag `vX.Y.Z`. `.github/workflows/release.yml` builds the four targets, publishes the
GitHub Release with tarballs, checksums and the shell installer, then `publish-tap.yml` updates the Homebrew
formula. Users install it as [`../install.md`](../install.md) says; a server takes it with
`deploy/install-linux.sh vX.Y.Z` ([`../ops-health-check.md`](../ops-health-check.md)).

## cargo-dist

`release.yml` is generated by [cargo-dist](https://axodotdev.github.io/cargo-dist/book/) at the version
`cargo-dist-version` pins, from `[workspace.metadata.dist]` in the root `Cargo.toml`. To change it: install
that version, take `allow-dirty` out of the config for a moment, run `dist generate --mode ci` (it refuses
otherwise), and put back the hand edits below.

The hand edits, each because dist has no setting for it, and which `tests/phase1_done.rs` checks:

1. **A stamp step** before the first `dist` call in `plan`, `build-local-artifacts`, `build-global-artifacts`
   and `host`: `python3 deploy/stamp_version.py "$GITHUB_REF_NAME"`. dist refuses a tag that is not the
   package's version, and the repo keeps `0.0.0` because the shipped version comes from the tag. The stamp
   only changes the job's checkout, and with no `ANNOTARY_VERSION` the binary reports `CARGO_PKG_VERSION`.
   It is skipped on a pull request, where dist only plans.
2. **`--generate-notes`** on `gh release create`: the notes list the merged pull requests, whose titles the
   `ci` job holds to Conventional Commits. dist alone only takes notes from a changelog file, and the repo
   keeps none.
3. **`permissions: contents: read`** on `custom-publish-tap`, in place of dist's id-token and package rights:
   that job pushes with the tap's deploy key and needs neither. It gets `HOMEBREW_TAP_DEPLOY_KEY` by name, in
   place of `secrets: inherit`.
4. **`contents: read` at the top, and `write` only on `host`**, in place of dist's `write` for every job: `plan`
   and the build jobs run a pull request's code. Only `gh release create` writes; dist's `host` steps do nothing
   on GitHub for GitHub hosting (`cargo-dist/src/host.rs`).
5. **Every action pinned to a full SHA**, with its version in a comment, in all four workflows, in place of `@v6`
   and the like. To move one, read the SHA with `gh api repos/OWNER/REPO/commits/TAG --jq .sha`.
6. **The dist installer checked before it runs**, in `plan` and in `build-local-artifacts` (which replaces
   dist's `${{ matrix.install_dist.run }}`): it is fetched from the exact release's URL and held to a SHA-256.
   The release publishes no `.sha256` for the installer and its `sha256.sum` leaves it out, so the value is the
   digest GitHub reports for the asset (`gh api repos/axodotdev/cargo-dist/releases/tags/v0.33.1`; the release is
   immutable), and the installer carries the checksum of the tarball it downloads. A new `cargo-dist-version`
   needs both the URL and the digest changed.

## The tap

dist's `homebrew` publish job needs a personal access token (`HOMEBREW_TAP_TOKEN`) and writes a formula with
no `test do`, so `publish-jobs` names our own workflow, `publish-tap.yml`. Its `check` job, with no secret, takes
dist's generated `annotary.rb`, adds the test and rewrites what `brew audit --strict` refuses in dist's output, the `version` line and the alias table (`deploy/tap_formula.py`; if dist changes its shape, the audit stops the job), and puts it in a local tap for `brew
audit --strict --online`, `brew install` and `brew test`. Only then does its `push` job, on a runner of its own,
check out `josh-andrews-dev/homebrew-tap` with the key, commit that same file and push. A failure leaves the tap
on the previous release, and the release itself up.

It pushes with `HOMEBREW_TAP_DEPLOY_KEY`, this repo's secret: the private half of a deploy key on the tap with
write access. It can write to that one repo and nothing else, it needs no personal token, and a fork's pull
request never sees it, because the job only runs on a pushed tag. It is never on a runner with Homebrew's action,
Homebrew or the release's binary: third-party code that went wrong there still could not push a formula to users.

The tarball carries `annotary.service` and `healthcheck.sh` (dist's `include`) beside the binary, and dist adds
`README.md`, `LICENSE-MIT` and `LICENSE-APACHE`. `deploy/install-linux.sh` refuses any other member, so a file
added there (a `CHANGELOG.md`, which dist would pick up by itself) changes its list too. So a server's install comes
from one checked file. The formula leaves them in its `pkgshare`, unused.

## The update notice

`crates/annotary/src/update.rs`, used by `-V` and `serve` start, and nothing else. `tests/update_notice.rs`
runs it through the binary against a fake Releases API: `ANNOTARY_UPDATE_URL` points the check there, and
`ANNOTARY_TTY=1` stands in for a terminal.

- A check is due once a day. The attempt is written before the request, so a failure or a second process does
  not ask again, and a data dir it cannot write means no request.
- `-V` asks only on a terminal, bounded by a 3 s timeout, so a script or an agent never waits on the network;
  anywhere, what the cache knows goes to stderr. `serve` asks on a thread of its own, after it starts
  listening, and logs what it learns. It runs once per start, so a long-running server hears at its next start.
- A build reporting `0.0.0` (a checkout, every test and perf run) has nothing to compare, so it never asks.
  That is what keeps the test suite off the network, with nothing for a harness to remember to set.
- Off with `update_check = false` in `config.toml` or `ANNOTARY_UPDATE_CHECK=off`.
