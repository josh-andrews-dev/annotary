The problem

Feedback on documents gets lost between agents

You write plans, specs and notes in Markdown with several coding agents and move the work between them. The feedback on those documents has nowhere durable to live.

Comments inside agent tools

Antigravity artifacts, plan-mode comments, desktop review panes.

  • One-shot: no replies, no resolution
  • Gone after the next edit
  • The next session, or another vendor's agent, can't see them

Google Docs

Gets comments-under-edits right, for people.

  • Agents can't read it in a few dozen tokens
  • Not your Markdown files
  • Hosted; no Version an approval can be tied to

GitHub pull requests

Great for code review.

  • Comments attach to lines, not phrases
  • A changed line makes its comment "outdated"
  • No cheap way for an agent to wait for you

What annotary is built to do

✓ Comment on a span, the whole Document, or an image
✓ Threads with replies, resolve and reopen
✓ Comments follow the text across Versions, or say honestly that they lost it
✓ Approve / Send back, recorded on a specific Version
✓ People and agents are Members with equal standing
✓ Agents read it through a CLI in a few dozen tokens
✓ Agents block until something needs them, without polling
✓ Runs on your machine; the data is plain files
What it is

One binary, three faces

annotary is a single Rust binary. It is the CLI that people and agents type, the local server that holds the truth, and the web page you read and comment in.

⌨︎

CLI

Push and pull Documents, list and reply to Threads, take Actions, wait for events. Plain tab-separated output, --json when a program parses it, typed exit codes.

Used by you and by every agent, through the same commands.

▣

Local server

annotary serve, or a macOS LaunchAgent via daemon install. Listens on 127.0.0.1:7377 only. SQLite + content-addressed files under ~/.annotary/.

Stores, authorizes and serves. Does no heavy work.

◧

Web viewer

Open http://127.0.0.1:7377. Rendered Markdown with Thread cards in the margin, select-to-comment, keyboard shortcuts, live updates, older Versions as they were.

On your own machine you are signed in automatically.

Under the hood

How re-anchoring works

It is a pure function of two texts, with no fuzzy matching, randomness or time limits. The same push always gives the same placements.

1 · lines

Histogram line diff

Find which lines are equal and which hunks changed (the imara-diff crate).

2 · words

Word diff inside each hunk

Inside a changed hunk, diff Unicode word tokens (UAX #29), not characters, so a rewritten sentence doesn't "survive" by sharing stray letters.

3 · survivors

Keep what survived

The new span runs from the first to the last surviving character of the old one. Insertions inside are covered; additions at the edges are not.

4 · verdict

Anchored, refined or orphaned

Same text ⇒ anchored. Some words survive ⇒ refined, with the current text. No word survives ⇒ orphaned, permanently.

Computed where you push

The CLI does the mapping when you push and sends the placements with the commit. The server recomputes and refuses any that don't match, because a wrong placement would corrupt that Anchor for good.

History stays small

Each Anchor keeps its original placement (frozen as the Thread's label), its current one, and a history entry only when something changed. That is enough to show any Thread "as it was" on any Version.

Checked against real cases

A table of fixtures drawn from Google Docs and GitHub behavior (D1–D12, G0–G14). Every row is a test, and the algorithm only changes when that table changes with it.

Orphaned is sticky and honest. If deleted text comes back in a later Version, the Thread stays orphaned rather than guessing that it is the same text. Orphaned Threads stay open, replyable and resolvable.

Try it · Actions

Decisions belong to a Version

An Action such as Approve or Send back is recorded on the head Version. A new Version starts with no Action, so an approval never quietly carries over to text nobody approved.

Guarded command: act plan approve --version

Declared, not hard-coded

Each Vault has default Actions (approve, send-back), and a Document can declare its own set. Each has a label and an intent: positive, neutral or negative.

Guarded by Version

--version N makes act and thread new refuse with exit 5 if someone pushed since you read. You never approve text you haven't seen.

A full log

actions plan lists every Action ever taken, with who, when and on which Version. list --action none finds what still needs a decision.

Try it · wait

Agents block until something needs them

annotary wait parks on the server and returns when a matching event lands. By default that means a new Version, an Action, or an @mention of this agent. Act as the human on the right and see which events wake it.

The cursor (seq) survives server restarts, so no event is missed or seen twice.

You, in the browser

Events log on the server

Wider filters are available with --on thread,reply,resolve,reopen or --action approve. Timeouts default to 30 minutes (exit 7). The same event stream drives the web page's live updates over Server-Sent Events.

Teaching the agent

A 59-line skill file is the whole manual

The binary carries an Agent Skills file. annotary skill install writes it where Claude Code, Codex and other tools look for skills. It costs about 940 tokens to load.

--- name: annotary description: Read, reply to and resolve review Threads on Markdown Documents shared via annotary; push new Versions; take Actions (approve, send back); wait for @mentions. … metadata: version: 0.1.0 --- ## Do this - Read through the CLI, never the file. annotary show DOC (~200 tokens) is the read path. - Cite Threads by id + quoted text (t7 "testable in isolation"), never by line number. - Pull before you edit, push when done. - Reply on the Thread, then resolve. - Guard with --version N on act and thread new. - Wait, don't poll. - --json when you will parse. ## Exit codes 0 ok · 1 usage · 2 not found · 3 no credential · 4 missing right · 5 conflict · 6 unreachable · 7 timeout

Rules that keep agents cheap and correct

  • Quote, don't cite line numbers. Line numbers belong to one Version; t7 "quoted text" stays meaningful.
  • Say what changed and where. “Done in v5: item 3 now reads …”, then --resolve.
  • Use @handle when a person needs to look; it wakes their wait.

Kept current by version

The skill records the binary version it shipped with. If annotary --version differs, the agent runs skill install again. It never overwrites a file you edited unless you pass --force.

Works with any agent tool

There is no plug-in and no MCP server to configure: anything that can run a shell command and read its output can be a Member. Each agent gets its own Token through ANNOTARY_TOKEN.

Technical · data

Where everything lives

Two places: the server's data directory, and your working folder, where pull writes the Markdown and its Sidecar. Click any file.

A Sidecar, abridged (plan.annotary)

The Sidecar is a deterministic, stable JSON projection of everything the server knows about the Document. On push the CLI reads only three things from it: the Document id, the base Version, and any Action declaration.

Technical · runtime

Heavy work happens where you push

The project's first design decision (ADR 0001): every per-Version computation runs in the CLI that pushes. The server only stores, authorizes and serves, so viewing a Document is a SQLite read plus static files.

The pushing CLI computes

  1. SHA-256 of the Markdown and every Asset
  2. The Asset scan: follows links, finds what's missing
  3. Image dimensions; PNG/JPEG copies of HEIC, AVIF, TIFF
  4. The diff and every Thread's new placement
  5. Markdown → HTML: GFM, tables, footnotes, math as MathML
  6. Uploads only the blobs the server lacks
→

The server stores and serves

  1. Checks rights, size limits and the manifest
  2. Verifies the submitted placements
  3. Commits Version, Threads and events in one transaction
  4. Serves pages with the Threads already in the HTML
  5. Streams events to wait and open pages
  6. Hourly housekeeping: auto-purge, blob cleanup

Local only, on purpose

It binds to 127.0.0.1 and refuses any other address, so nothing on your network can reach it. In a browser on the same machine you're the owner automatically, unless you set a local password.

Always on

daemon install writes a macOS LaunchAgent that starts at login and restarts if it stops. status, start, stop, restart and uninstall manage it. On Linux, run serve under your own service manager.

Why the split matters later

When a hosted version exists, the expensive work still runs on your machine, so a cloud server stays cheap. The same split lets a browser push through WebAssembly; the renderer and diff crates already compile for it.

Try it · access

People and agents are both Members

Nothing in the model distinguishes a person from an agent. The only difference is how they sign in: a local password, or a Token. Rights are granted per Vault. Pick a Member to see what they can do.

One command per Member

member add codex creates the Member with full rights and prints ANNOTARY_TOKEN=… once. Set it where the Member runs annotary and you're done. The web UI has an equivalent "Add member" button.

Tokens you can audit

token list shows when each Token was last used. Tokens can carry an expiry and are revoked with one command. They are stored hashed.

History is never lost

Members are disabled, never deleted, and a handle is never reused. Every mutation writes an event in the same transaction, so who did what is always on record.

Technical · Assets

Images, video and PDFs travel with the Document

Any local file your Markdown links to becomes an Asset of that Version, stored once by its content hash however many Versions use it.

What counts

png jpg gif webp svg heic heif avif tiff bmp · mp4 mov m4v webm · mp3 m4a aac wav ogg flac · pdf · md markdown txt

Linked Markdown files are followed up to five levels deep. Code blocks are never mistaken for links.

Missing is shown, not fatal

A file that isn't there still lets the push go through. You get a warning, the page shows a placeholder, and --strict turns warnings into a refusal.

Comment on an image

thread new plan --asset img/architecture.png. Asset Threads follow the file's content: if the image is replaced or removed, the Thread is orphaned.

Ready for the browser

Width and height are recorded at push, so pages never jump while images load. HEIC and AVIF photos get a JPEG copy, and TIFF/BMP a PNG.

Uploads only what's new

The CLI asks the server which hashes it lacks and sends only those. Re-pushing a Document with 40 images uploads none of them.

Size limits

2 MB of Markdown, 100 MB per Asset, 500 MB per Version. The CLI checks them before uploading and the server enforces them again.

Get started

Five minutes to your first review

# 1. start the server (first run asks for your handle) annotary daemon install # 2. give an agent its own Member annotary member add claude-code ANNOTARY_TOKEN=ant_… ← paste into the agent's env # 3. teach it the commands annotary skill install # 4. share a document annotary push plan.md -m "first draft" # 5. open it and start commenting open http://127.0.0.1:7377

Then ask your agent to “address the review comments on plan”. It will show, pull, edit, push, reply on each Thread and resolve it. It can wait for your approval without using any tokens while it waits.
